## Goal

Move the **room authoring tool** out of v2 and into this project, so that authored rooms bake
directly into v1's `Master_Room` contract and drop straight into v1's existing Blueprint
generator with no converter.

- **v1 — this project.** `E:\UE5 Projects\UE5_Procedural_Level_Generator`, project
  `Procedural_Dongeon`, UE 5.8. Its Blueprint dungeon generator stays as-is and is the level
  generator of record. Its C++ module is an empty stub — `MyObject.h` is a bare `UObject`.
- **v2 — the source of the port.** `E:\UE5 Projects\Level_Creator_1`, UE 5.8. Keep it open for
  reference. Nothing there gets deleted.

This follows the 2026-09-07 direction change, recorded in v2's
`production/session-state/active.md` and `docs/superpowers/specs/2026-09-07-kit-sets-design.md`:
*v1 generates levels, v2 becomes the room authoring tool.* Moving the tool into v1 is the
extension of that decision, and it **eliminates** the v1/v2 seam that kit-set spec §6 deferred as
"a real and separate piece of work" — the bake targets v1's contract instead of needing a
converter afterwards.

## Decisions already made — do not reopen

**1. The bake emits `Master_Room_C` children, not `URectRoomAsset`.**
Exit arrows under `Exits Folder`, `Overlap_Box` on the `RoomOverlap` channel, floor at Z=0,
origin at the entrance. `URectRoomAsset`'s room-pool fields (`Role`, `Weight`, `MaxPlacements`)
belong to v2's dormant solver and do not come across. Its dressing fields are what the kit set
replaces. This settles kit-set spec §7's open question 2.

**2. One baked Blueprint per exit.**
A v1 room piece has exactly one entrance — its origin (see Verified facts). A grid-authored room
with N symmetric exits therefore bakes to N Blueprints, each rebased so a different exit sits at
the origin. They are derived data, regenerated by the bake, so the cost is disk rather than
authoring. This is the only way such a room can be entered from more than one side.

**3. Rename the module before porting anything.**
`Procedural_Dongeon` → `ProceduralDungeon`. Do it while the module holds nothing but the stub —
that is the cheapest this rename will ever be, and the ~5,700 ported lines would otherwise all
carry `PROCEDURAL_DONGEON_API`. Touches the `.uproject`, `Build.cs`, both `Target.cs` files, and
needs project files regenerated.

**4. Kit sets bind by reference with fallback.**
`UDungeonKitSet` is a `UDataAsset` naming one asset per structural role. `URoomRecipeAsset` holds
the set; a chamber's existing piece slot now means *override*, and empty means inherit. Editing a
set fixes every room that uses it.

- Use `FSoftClassPath` / `FSoftObjectPath`, **not** `TSubclassOf` as kit-set spec §3.1 says. The
  consumer at `RoomAuthorTools.cpp:2000` does `.ToString()` into PCG string params, so soft paths
  need no conversion, and it preserves the no-hard-references property `FRoomChamber`'s own
  comment spends a paragraph justifying.
- Ship the census's six assets as **constructor defaults**, so Phase 1 is testable with no editor
  and a `DA_KitSet_*` asset is a later convenience rather than a prerequisite.
- Name `WallCap` distinctly from `Door`. `BP_COMP_Door_Walled_01_large` is a sealing cap, and
  using it as a passable door is what caused v2's 2026-08-28 sealed-doorway defect.
- `CeilingMesh` is unresolved: `FRoomChamber` has the pick but the census's six-asset set has no
  ceiling. Verify against a real room in the editor before choosing a default. **Do not guess a
  path into a constructor.**

## Verified facts — checked against the assets, not assumed

- **`Master_Room` components**, read from its name table:
  `DefaultSceneRoot`, `Arrow` (ArrowComponent), `Exits Folder`, `Overlap Folder` → `Overlap_Box`
  (BoxComponent), `FloorSpawnPoints`, `GeometryFolder`. HANDOFF.md §1.2 is accurate.
- **`RoomOverlap` is already declared** in this project's `Config/DefaultEngine.ini` as
  `ECC_GameTraceChannel1`. Nothing to port.
- **Origin-at-entrance is structural, not a convention.** HANDOFF.md §1.4's flow deferred-spawns
  each room at the selected exit's world transform; a centre pivot would drop the room's middle
  on the doorway. Hence decision 2 above. `1_Room1` and `1_StarterRoom` carry `Arrow`–`Arrow3`;
  `1_Hall1` carries two.
- **`FloorSpawnPoints` comes free from the chamber grid.** Every interior floor tile is a
  candidate point. This is HANDOFF.md §3.10's most powerful option — named unsolved twice in the
  tutorial — and it costs nothing because the grid already exists.
- **v1's content is still saved as `++UE5+Release-5.7`.** The `.uproject` says 5.8 but assets have
  not been resaved. They upgrade on load. Do the resave deliberately, in its own commit, rather
  than tangled into the port.
- **`Content/ProceduralLevel/Master_Room.uasset` is a redirector**, not a duplicate of
  `LevelPieces/Master_Room.uasset`. Not a hygiene problem.

## Traps and constraints

- **`read_graph_dsl` output does not re-parse.** Editing the EUW graph through MCP: the read form
  prints widget-call targets last, but the writer binds the first positional arg to `self`, so
  every widget call needs explicit `:self` / `:PinName` keywords. It also prints
  `Behavior|SetValue` for what is really `Class|SpinBox|SetValue`. Use `find_node_types` for an
  unambiguous id and `get_node_type_pins` for exact pin names. A failed write is atomic. Full
  detail in v2's `active.md` under 2026-09-07.
- **20 files are tracked under `Intermediate/`, `Saved/` and `Binaries/`** in this repo despite
  `.gitignore` covering all of them — they were committed before the ignore rules landed. This is
  why `git status` is dirty before anything is touched. Untrack them in their own commit.
- **`Config/DefaultGame.ini` still says `ProjectName=Third Person BP Game Template`.**
- The working tree already has uncommitted changes, including the staged C++ stub. Sort out what
  is kept before the module rename, not after.
